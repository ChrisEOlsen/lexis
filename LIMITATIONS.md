# Known Limitations

Deliberate MVP-scope tradeoffs, not bugs. Track file, limitation, future upgrade.

| File | Limitation | Future Upgrade |
|---|---|---|
| src/core/tokenizer.c | ASCII-only normalization. Any byte >= 0x80 treated as delimiter — non-ASCII text gets split/dropped (e.g. "café" → "caf", "é" lost) | Add UTF-8-aware case folding/normalization (e.g. utf8proc) or ICU if non-English corpora become a requirement (spec section 9) |
| src/core/tokenizer.c | Internal apostrophes no longer fragment ("don't" stays one token), but there's still no contraction/expansion normalization — "don't" and "do not" share zero tokens, and possessives aren't stripped ("Okafor's" stays "okafor's", won't match a bare "Okafor" elsewhere in the text). Deliberately not attempting to tell contraction from possessive by spelling alone — a strip-trailing-'s rule would silently turn "isn't" into "isn", inverting a negation | Contraction-expansion table or NLP-based normalization in Python sidecar (pairs with POS tagging, spec 5.2.2) — not the C tokenizer's job |
| src/core/tokenizer.c | Word buffer capped at 256 bytes (WORD_BUFFER_SIZE). Words/runs longer than that are silently truncated, not rejected or logged | Revisit only if real corpus data shows pathological long non-space runs; consider explicit rejection + logging instead of silent truncation |
| src/core/pg_store.c | pg_store_get_or_create_term()/pg_store_get_or_create_terms() use INSERT ... ON CONFLICT (term) DO NOTHING plus a re-SELECT, not DO UPDATE ... RETURNING id -- DO UPDATE takes a row lock even for a no-op self-assignment, and under real concurrent writers that caused genuine Postgres deadlocks (verified: "deadlock detected ... while inserting index tuple ... in relation terms"). DO NOTHING still doesn't eliminate deadlocks entirely -- Postgres's ON CONFLICT uses "speculative insertion" internally, and concurrent speculative inserts on the same unique index can still deadlock (also verified directly, same error, with DO NOTHING). This is exactly the contention bulk_ingest.c's three-phase design (see SPEED.md) was built to avoid structurally -- its Phase 2 worker pool never calls these functions at all, only Phase 3's single-writer finalize pass touches `terms` | These two functions currently have no production caller (bulk_ingest.c's Phase 2/3 use a different, staging-table-based path instead) -- kept as tested, documented PgStore API surface for any future caller needing single-term resolution outside the bulk pipeline |
| src/core/pg_store.c | postings stores one uncompressed SQL row per (term, passage) pair -- measured ~29.3 bytes/row (data + its B-tree index combined) on the SQLite version via dbstat; Postgres's row/index overhead is a different number but the same class of gap versus a real compressed inverted index (delta-encoded passage IDs + varint, e.g. Lucene/PISA-style, ~1-3 bytes/posting). Projected against MS MARCO's 8.8M passages (spec 8.2), a naive extrapolation put the SQLite schema's full index around ~14-15GB versus the ~1.5-2GB commonly cited for a compressed BM25 index over the same dataset -- not directly comparable formats, but a real footprint difference worth knowing about before a large ingest; not yet re-measured against Postgres's actual on-disk size | Replace one-row-per-posting with a compressed postings list per term (a delta-encoded/varint BLOB of passage_id+term_frequency pairs, decoded on read in bm25.c), matching real inverted-index compression at the cost of "postings queryable via plain SELECT" |
| src/core/ingest.c | ingest_read_file() loads an entire document into memory with no size guard. Assumes each document (a research paper, legal document, single codebase file, etc. per spec's own examples) is individually small — the corpus is many separate reasonably-sized files, not one unbounded blob | Add a max-file-size check (reject + log, don't silently attempt a huge malloc) if a real corpus ever presents a pathologically large single document; until then this is unexercised complexity |
| src/core/wordnet.c | wordnet_parse_data_line() assumes a hypernym/hyponym pointer's target synset shares the source synset's part of speech. Holds in practice for these two relations, but the file format technically allows cross-POS pointers | Store the pointer's own `pos` field (currently read and discarded) if a real lookup ever needs to follow a cross-POS hypernym/hyponym chain |
| src/core/wordnet.c | wordnet_load_data_file() treats any single unparseable line as a hard failure for the whole file, rather than skipping the bad line and continuing. Deliberate: this is trusted, official WordNet data, so a parse failure indicates a real bug in the parser, not malformed input worth silently tolerating | Revisit only if this is ever pointed at a modified/non-official WordNet distribution where a skip-and-continue policy might be more appropriate |
| (no current file -- Stage 6) | POS tagging is deferred entirely -- the query pipeline sends stopword-filtered terms straight to WordNet lookup with no noun/verb/adjective gate in front of it. Originally planned as a Python sidecar (spaCy) because the spec assumed synonym expansion itself would be the expensive step (Python/NLTK), making it worth pre-filtering first; once synonym expansion turned out to be a cheap local C hash table lookup (src/core/wordnet.c), that cost justification mostly evaporated, and the never-implemented sidecar scaffold (src/sidecar/, all empty stub files) was removed entirely rather than left as dead placeholder code. Stage 7's query formulation step already re-filters synonym candidates via its own LLM call, providing a downstream safety net against noise from any non-content words that survive stopword removal | Build a Python sidecar (spaCy) for POS tagging only if the benchmarking stage (spec section 8, MS MARCO comparison) shows measurably worse precision/recall without it -- not before, per the spec's own stated principle: "engineer for the problem you have, not the problem you might have" |
| src/core/query_formulation.c | Output is a flat, unweighted term list, not the spec's fuller vision of "a boolean BM25 query with phrase groupings and term weights" (5.2.4). Matches what bm25_search() can actually consume today -- no boolean operators, phrase grouping, or per-term weighting exist anywhere in bm25.c | Add per-term weighting to bm25_search()/bm25_term_score() first (a real change to already-tested retrieval code), then extend query formulation's prompt/parsing to produce weighted output, if flat-term-list precision proves insufficient in practice |
| src/core/query_formulation.c | query_formulation_build_prompt() caps each candidate category (synonyms/hypernyms/hyponyms) at 8 words per term (QUERY_FORMULATION_MAX_CANDIDATES) -- an arbitrary first-N cut, not a ranked top-N, since TokenList carries no relevance ordering, just synset-iteration order. A highly polysemous word (e.g. "dog": 29 synonyms, 41 hyponyms) has most of its candidates silently excluded from the prompt | Track some relevance/frequency signal during WordNet resolution (e.g. WordNet's own sense-ordering, which the current design discards) so the cap keeps the most useful candidates rather than whichever happened to be encountered first |
| src/core/main.c | `lexis bulk-ingest <tsv_path>` never clears the existing index first -- it only appends. Running it twice on the same corpus duplicates every passage rather than replacing them (terms stay correct via Phase 3's ON CONFLICT DO NOTHING dedup, but passage rows and therefore BM25's corpus stats double) | Add a `--rebuild` flag (or make it the default) that truncates passages/terms/postings before ingesting, or detect and skip documents already present by name |
| src/core/main.c | Model path (LEXIS_MODEL_PATH), chunk size/overlap (200/40), top-K (5), and all data paths are still hardcoded constants in main.c -- config/lexis.conf now exists and is parsed (config.c), but only for the testing/production `mode` setting, not these | Extend config.c's parser to cover these too, if hardcoded defaults ever prove insufficient for real use |
| src/core/local_llm_client.c | Full OpenRouter-to-local migration (openrouter_client.c/.h deleted): both LLM call sites (query formulation, generation) now run Llama-3.2-3B-Instruct-Q4_K_M via llama.cpp's embedded C API, chosen after rejecting the OpenRouter API's per-query cost for a ~9,260-query MRR@10/Recall@K eval, and Ollama's separate-HTTP-server model in favor of true in-process linking (matching the project's native-app direction). Verified real: linked a standalone test program against `llama.h`/`libllama.dylib` (Homebrew, /opt/homebrew/Cellar/llama.cpp), ran a real generation, and confirmed Metal GPU offload auto-detects with a ~5.7GB recommendedMaxWorkingSetSize on this 8GB M2 -- the real number the model size was chosen against, since Postgres and the OS both need headroom on the same machine. (Originally measured while Postgres still ran under Docker Desktop, which needed more headroom than the native install this project later moved to entirely -- see CURRENT_STATE.md) | Not yet measured under concurrent load -- revisit if Metal + Postgres memory pressure ever becomes a real problem in practice |
| src/core/local_llm_client.c | main.c's run_query() loads the model fresh (llama_model_load_from_file + Metal shader compilation) on every single CLI invocation -- measured ~9-19s of that one-time cost per process, dominating a single query's wall time. Fine for one-off CLI queries; would be a real problem for the paused MS MARCO eval plan (~9,260 queries), which needs the model loaded once and reused across the whole run, not re-loaded per query | Before resuming the MS MARCO eval, build the eval harness as a single long-running process (or a persistent query-serving mode) that calls local_llm_client_init() once and loops queries through it, instead of shelling out to the `lexis` CLI per query |
| src/core/local_llm_client.c | Sampling is greedy-only (llama_sampler_init_greedy(), no temperature/top-p/repetition penalty) -- deterministic and cheap, matching "fast, not creative," but with no repetition penalty a long grounded-generation prompt could in principle degenerate into token loops; not observed in manual testing so far, not yet stress-tested against long/adversarial contexts. n_ctx/n_batch are also fixed at 4096, sized for TOP_K=5 passages at the current 200-token chunk size -- a prompt that doesn't fit is rejected cleanly (logged, returns NULL) rather than truncated or chunked | Add a repetition penalty sampler (llama_sampler_init_penalties()) if looping is ever observed in practice; revisit the 4096 context size if TOP_K or chunk_size grow enough to risk overflowing it |

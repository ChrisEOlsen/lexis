# Known Limitations

Deliberate MVP-scope tradeoffs, not bugs. Track file, limitation, future upgrade.

| File | Limitation | Future Upgrade |
|---|---|---|
| src/core/tokenizer.c | ASCII-only normalization. Any byte >= 0x80 treated as delimiter — non-ASCII text gets split/dropped (e.g. "café" → "caf", "é" lost) | Add UTF-8-aware case folding/normalization (e.g. utf8proc) or ICU if non-English corpora become a requirement (spec section 9) |
| src/core/tokenizer.c | Internal apostrophes no longer fragment ("don't" stays one token), but there's still no contraction/expansion normalization — "don't" and "do not" share zero tokens, and possessives aren't stripped ("Okafor's" stays "okafor's", won't match a bare "Okafor" elsewhere in the text). Deliberately not attempting to tell contraction from possessive by spelling alone — a strip-trailing-'s rule would silently turn "isn't" into "isn", inverting a negation | Contraction-expansion table or NLP-based normalization in Python sidecar (pairs with POS tagging, spec 5.2.2) — not the C tokenizer's job |
| src/core/tokenizer.c | Word buffer capped at 256 bytes (WORD_BUFFER_SIZE). Words/runs longer than that are silently truncated, not rejected or logged | Revisit only if real corpus data shows pathological long non-space runs; consider explicit rejection + logging instead of silent truncation |
| src/core/pg_store.c | pg_store_get_or_create_term()/pg_store_get_or_create_terms() use INSERT ... ON CONFLICT (term) DO NOTHING plus a re-SELECT, not DO UPDATE ... RETURNING id -- DO UPDATE takes a row lock even for a no-op self-assignment, and under real concurrent writers (concurrent_ingest.c) that caused genuine Postgres deadlocks (verified: "deadlock detected ... while inserting index tuple ... in relation terms"). DO NOTHING still doesn't eliminate deadlocks entirely -- Postgres's ON CONFLICT uses "speculative insertion" internally, and concurrent speculative inserts on the same unique index can still deadlock (also verified directly, same error, with DO NOTHING). concurrent_ingest.c retries a whole document's ingestion up to 3 times on any failure to recover, per Postgres's own documented guidance that applications should retry rather than try to structurally prevent this class of deadlock | If deadlock frequency ever becomes a real throughput problem (not yet measured as one -- retries were rare enough not to show up in the 4-thread benchmark numbers), consider an advisory lock per term (pg_advisory_xact_lock(hashtext(term))) to serialize writers on the same term specifically -- adds a round trip in the common case, so only worth it if retries start actually costing more than that would |
| src/core/pg_store.c | postings stores one uncompressed SQL row per (term, passage) pair -- measured ~29.3 bytes/row (data + its B-tree index combined) on the SQLite version via dbstat; Postgres's row/index overhead is a different number but the same class of gap versus a real compressed inverted index (delta-encoded passage IDs + varint, e.g. Lucene/PISA-style, ~1-3 bytes/posting). Projected against MS MARCO's 8.8M passages (spec 8.2), a naive extrapolation put the SQLite schema's full index around ~14-15GB versus the ~1.5-2GB commonly cited for a compressed BM25 index over the same dataset -- not directly comparable formats, but a real footprint difference worth knowing about before a large ingest; not yet re-measured against Postgres's actual on-disk size | Replace one-row-per-posting with a compressed postings list per term (a delta-encoded/varint BLOB of passage_id+term_frequency pairs, decoded on read in bm25.c), matching real inverted-index compression at the cost of "postings queryable via plain SELECT" |
| src/core/ingest.c | ingest_read_file() loads an entire document into memory with no size guard. Assumes each document (a research paper, legal document, single codebase file, etc. per spec's own examples) is individually small — the corpus is many separate reasonably-sized files, not one unbounded blob | Add a max-file-size check (reject + log, don't silently attempt a huge malloc) if a real corpus ever presents a pathologically large single document; until then this is unexercised complexity |
| src/core/ingest.c | ingest_corpus() is non-recursive — only ingests files directly inside the given directory; subdirectories are silently skipped entirely, not descended into | Add recursive directory walking (nftw() or manual recursion via opendir/readdir) if a real corpus is ever organized into nested folders rather than one flat directory |
| src/core/ingest.c | ingest_corpus() itself is still single-threaded/single-connection -- concurrent_ingest.c is the concurrent path (spec section 6's pthreads plan), a separate function, not a change to ingest_corpus()/main.c's CLI, which still calls the sequential version. Real measured numbers on the realistic 3,000-document benchmark corpus (56 words/passage, 20k-word vocab, matching MS MARCO's published stats): pg_store_get_or_create_term()/insert_posting() calling one round trip per term was the dominant cost once SQLite's transaction-per-statement problem was fixed (~0.13ms/round-trip against this project's Docker Postgres, ~35 round trips/document) -- single-threaded Postgres ingestion was initially *slower* than the SQLite version it replaced (60.5 vs ~569 passages/sec) until pg_store_get_or_create_terms()/pg_store_insert_postings() batched a whole chunk's terms into a handful of round trips regardless of term count, bringing single-threaded throughput to 476.7 passages/sec. Layering concurrent_ingest_corpus() on top of the batched code got to 1866.1 passages/sec at 4 threads (the sweet spot on an 8-logical-core machine; 8 threads regressed to 1195.2/sec from deadlock retries plus real CPU contention) -- roughly 1.3 hours projected for MS MARCO's 8.8M passages, down from ~4.8 hours single-threaded SQLite and ~3.3 hours for the best the sharded-SQLite experiment (experiment/sharded-ingestion branch) ever achieved | main.c's `lexis ingest` still calls the sequential ingest_corpus(), not concurrent_ingest_corpus() -- wire it in (with a thread-count flag/config value) if this branch's approach is adopted for real ingestion, not just benchmarking. Also worth profiling thread counts above 8 differently (e.g. bounding by physical, not logical, core count) if this ever needs to scale on a bigger machine |
| src/core/wordnet.c | wordnet_parse_data_line() assumes a hypernym/hyponym pointer's target synset shares the source synset's part of speech. Holds in practice for these two relations, but the file format technically allows cross-POS pointers | Store the pointer's own `pos` field (currently read and discarded) if a real lookup ever needs to follow a cross-POS hypernym/hyponym chain |
| src/core/wordnet.c | wordnet_load_data_file() treats any single unparseable line as a hard failure for the whole file, rather than skipping the bad line and continuing. Deliberate: this is trusted, official WordNet data, so a parse failure indicates a real bug in the parser, not malformed input worth silently tolerating | Revisit only if this is ever pointed at a modified/non-official WordNet distribution where a skip-and-continue policy might be more appropriate |
| src/sidecar/ (Stage 6) | POS tagging is deferred entirely -- the query pipeline sends stopword-filtered terms straight to WordNet lookup with no noun/verb/adjective gate in front of it. Originally planned because the spec assumed synonym expansion itself would be the expensive step (Python/NLTK), making it worth pre-filtering first; once synonym expansion turned out to be a cheap local C hash table lookup (src/core/wordnet.c), that cost justification mostly evaporated. Stage 7's query formulation step already re-filters synonym candidates via its own LLM call, providing a downstream safety net against noise from any non-content words that survive stopword removal | Stand up the Python sidecar (spaCy) for POS tagging only if the benchmarking stage (spec section 8, MS MARCO comparison) shows measurably worse precision/recall without it -- not before, per the spec's own stated principle: "engineer for the problem you have, not the problem you might have" |
| src/core/query_formulation.c | Output is a flat, unweighted term list, not the spec's fuller vision of "a boolean BM25 query with phrase groupings and term weights" (5.2.4). Matches what bm25_search() can actually consume today -- no boolean operators, phrase grouping, or per-term weighting exist anywhere in bm25.c | Add per-term weighting to bm25_search()/bm25_term_score() first (a real change to already-tested retrieval code), then extend query formulation's prompt/parsing to produce weighted output, if flat-term-list precision proves insufficient in practice |
| src/core/query_formulation.c | query_formulation_build_prompt() caps each candidate category (synonyms/hypernyms/hyponyms) at 8 words per term (QUERY_FORMULATION_MAX_CANDIDATES) -- an arbitrary first-N cut, not a ranked top-N, since TokenList carries no relevance ordering, just synset-iteration order. A highly polysemous word (e.g. "dog": 29 synonyms, 41 hyponyms) has most of its candidates silently excluded from the prompt | Track some relevance/frequency signal during WordNet resolution (e.g. WordNet's own sense-ordering, which the current design discards) so the cap keeps the most useful candidates rather than whichever happened to be encountered first |
| src/core/main.c | `lexis ingest <corpus_dir>` never clears the existing index first -- it only appends. Running it twice on the same corpus duplicates every passage rather than replacing them (terms/postings stay correct via get_or_create_term's dedup, but passage rows and therefore BM25's corpus stats double) | Add a `--rebuild` flag (or make it the default) that deletes the existing index file before ingesting, or detect and skip documents already present by name |
| src/core/main.c | Model path (LEXIS_MODEL_PATH), chunk size/overlap (200/40), top-K (5), and all data paths are still hardcoded constants in main.c -- config/lexis.conf now exists and is parsed (config.c), but only for the testing/production `mode` setting, not these | Extend config.c's parser to cover these too, if hardcoded defaults ever prove insufficient for real use |
| src/core/local_llm_client.c | Full OpenRouter-to-local migration (openrouter_client.c/.h deleted): both LLM call sites (query formulation, generation) now run Llama-3.2-3B-Instruct-Q4_K_M via llama.cpp's embedded C API, chosen after rejecting the OpenRouter API's per-query cost for a ~9,260-query MRR@10/Recall@K eval, and Ollama's separate-HTTP-server model in favor of true in-process linking (matching the project's native-app direction). Verified real: linked a standalone test program against `llama.h`/`libllama.dylib` (Homebrew, /opt/homebrew/Cellar/llama.cpp), ran a real generation, and confirmed Metal GPU offload auto-detects with a ~5.7GB recommendedMaxWorkingSetSize on this 8GB M2 -- the real number the model size was chosen against, since Docker Postgres and the OS both need headroom on the same machine | If Metal + Postgres memory pressure ever becomes a real problem (not yet measured under concurrent load), the documented fallback is moving Postgres out of Docker Desktop to a native Homebrew install to shrink its footprint |
| src/core/local_llm_client.c | main.c's run_query() loads the model fresh (llama_model_load_from_file + Metal shader compilation) on every single CLI invocation -- measured ~9-19s of that one-time cost per process, dominating a single query's wall time. Fine for one-off CLI queries; would be a real problem for the paused MS MARCO eval plan (~9,260 queries), which needs the model loaded once and reused across the whole run, not re-loaded per query | Before resuming the MS MARCO eval, build the eval harness as a single long-running process (or a persistent query-serving mode) that calls local_llm_client_init() once and loops queries through it, instead of shelling out to the `lexis` CLI per query |
| src/core/local_llm_client.c | Sampling is greedy-only (llama_sampler_init_greedy(), no temperature/top-p/repetition penalty) -- deterministic and cheap, matching "fast, not creative," but with no repetition penalty a long grounded-generation prompt could in principle degenerate into token loops; not observed in manual testing so far, not yet stress-tested against long/adversarial contexts. n_ctx/n_batch are also fixed at 4096, sized for TOP_K=5 passages at the current 200-token chunk size -- a prompt that doesn't fit is rejected cleanly (logged, returns NULL) rather than truncated or chunked | Add a repetition penalty sampler (llama_sampler_init_penalties()) if looping is ever observed in practice; revisit the 4096 context size if TOP_K or chunk_size grow enough to risk overflowing it |
| src/core/term_cache.c | Single global mutex guards the whole shared hash table -- every worker thread's cache lookup/insert serializes on it, even though the critical section itself is tiny (pure in-memory hash probes, no Postgres calls while held). Not yet measured as an actual bottleneck at 4 threads (the real fix's ~1.7x measured speedup already accounts for whatever this mutex costs), but could start to matter at much higher thread counts than this project has ever benefited from anyway (see the thread-count sweep in SPEED.md -- throughput collapses past ~16 threads for unrelated Postgres-contention reasons first) | Lock striping (N mutexes, term's hash selects which one) if a future higher-concurrency scenario ever shows real contention on this specific mutex, not before |
| src/core/term_cache.c | Real MS MARCO scale (3.49M distinct terms) also revealed a genuine correctness bug in this module's first version, since fixed: writing a newly-resolved (term, id) pair straight into the shared cache before its document's transaction actually commits let a later rollback (e.g. a deadlock on a subsequent chunk) leave a phantom, never-persisted term_id permanently cached -- verified directly (real foreign-key violations, `postings_term_id_fkey`, cascading across the rest of a run). Fixed via a document-local TermCachePending list, only merged into the shared cache after a successful commit; regression-tested (`test_pending_discarded_on_rollback_does_not_poison_cache`). Documented here as a reminder of the invariant this module depends on: the shared cache must never contain a term_id that isn't already durably committed | None currently planned -- the invariant is now enforced structurally (term_cache_get_or_create_terms() has no way to write the shared cache directly, only via term_cache_commit_pending()) |

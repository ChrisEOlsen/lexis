# Known Limitations

Deliberate MVP-scope tradeoffs, not bugs. Track file, limitation, future upgrade.

| File | Limitation | Future Upgrade |
|---|---|---|
| src/core/tokenizer.c | ASCII-only normalization. Any byte >= 0x80 treated as delimiter — non-ASCII text gets split/dropped (e.g. "café" → "caf", "é" lost) | Add UTF-8-aware case folding/normalization (e.g. utf8proc) or ICU if non-English corpora become a requirement (spec section 9) |
| src/core/tokenizer.c | Internal apostrophes no longer fragment ("don't" stays one token), but there's still no contraction/expansion normalization — "don't" and "do not" share zero tokens, and possessives aren't stripped ("Okafor's" stays "okafor's", won't match a bare "Okafor" elsewhere in the text). Deliberately not attempting to tell contraction from possessive by spelling alone — a strip-trailing-'s rule would silently turn "isn't" into "isn", inverting a negation | Contraction-expansion table or NLP-based normalization in Python sidecar (pairs with POS tagging, spec 5.2.2) — not the C tokenizer's job |
| src/core/tokenizer.c | Word buffer capped at 256 bytes (WORD_BUFFER_SIZE). Words/runs longer than that are silently truncated, not rejected or logged | Revisit only if real corpus data shows pathological long non-space runs; consider explicit rejection + logging instead of silent truncation |
| src/core/sqlite_store.c | sqlite_store_get_or_create_term() does a SELECT then, if empty, an INSERT — not atomic. Under concurrent ingestion (spec's pthreads stage), two threads could both miss the SELECT and both attempt the INSERT for the same new term | terms.term has a UNIQUE constraint, so the losing INSERT fails loudly rather than duplicating a row — but the function doesn't yet handle that failure by retrying the SELECT. Add that retry (or serialize term creation behind a mutex) once ingestion is actually made concurrent |
| src/core/sqlite_store.c | postings stores one uncompressed SQL row per (term, passage) pair -- measured ~29.3 bytes/row (data + its B-tree index combined) via sqlite3's dbstat virtual table on a synthetic benchmark corpus. A real compressed inverted index (delta-encoded passage IDs + varint, e.g. Lucene/PISA-style) gets down to ~1-3 bytes/posting -- roughly a 10-30x gap. Projected against MS MARCO's 8.8M passages (spec 8.2), that puts our schema's full index on the order of ~14-15GB versus the ~1.5-2GB commonly cited for a compressed BM25 index over the same dataset -- not directly comparable formats, but a real footprint difference worth knowing about before a large ingest | Two tiers: (1) cheap -- switch postings to a WITHOUT ROWID table, since SQLite currently stores both an implicit rowid and our explicit (term_id, passage_id) index redundantly; (2) bigger -- replace one-row-per-posting with a compressed postings list per term (a delta-encoded/varint BLOB of passage_id+term_frequency pairs, decoded on read in bm25.c), matching real inverted-index compression at the cost of "postings queryable via plain SELECT" |
| src/core/ingest.c | ingest_read_file() loads an entire document into memory with no size guard. Assumes each document (a research paper, legal document, single codebase file, etc. per spec's own examples) is individually small — the corpus is many separate reasonably-sized files, not one unbounded blob | Add a max-file-size check (reject + log, don't silently attempt a huge malloc) if a real corpus ever presents a pathologically large single document; until then this is unexercised complexity |
| src/core/ingest.c | ingest_corpus() is non-recursive — only ingests files directly inside the given directory; subdirectories are silently skipped entirely, not descended into | Add recursive directory walking (nftw() or manual recursion via opendir/readdir) if a real corpus is ever organized into nested folders rather than one flat directory |
| src/core/ingest.c | ingest_corpus() is single-threaded -- one document at a time, no parallelism, despite pthreads being in the spec's own tech stack (section 6) specifically for "parallel document ingestion for large corpora." Measured on a synthetic 3,000-document corpus after wrapping each document's writes in one SQLite transaction (see git history for the before/after): ~183 passages/sec. Extrapolated to MS MARCO's 8.8M passages (spec 8.2), that's roughly 13 hours for a single-threaded full ingest -- a real number, not a guess, but still not "minutes" | Add pthreads-based concurrent ingestion (spec's own plan) if a full MS MARCO ingest or similar corpus scale is actually attempted; note SQLite's single-writer-at-a-time semantics would then become the real ceiling, not the transaction-per-statement pattern this entry's fix already addressed |
| src/core/wordnet.c | wordnet_parse_data_line() assumes a hypernym/hyponym pointer's target synset shares the source synset's part of speech. Holds in practice for these two relations, but the file format technically allows cross-POS pointers | Store the pointer's own `pos` field (currently read and discarded) if a real lookup ever needs to follow a cross-POS hypernym/hyponym chain |
| src/core/wordnet.c | wordnet_load_data_file() treats any single unparseable line as a hard failure for the whole file, rather than skipping the bad line and continuing. Deliberate: this is trusted, official WordNet data, so a parse failure indicates a real bug in the parser, not malformed input worth silently tolerating | Revisit only if this is ever pointed at a modified/non-official WordNet distribution where a skip-and-continue policy might be more appropriate |
| src/sidecar/ (Stage 6) | POS tagging is deferred entirely -- the query pipeline sends stopword-filtered terms straight to WordNet lookup with no noun/verb/adjective gate in front of it. Originally planned because the spec assumed synonym expansion itself would be the expensive step (Python/NLTK), making it worth pre-filtering first; once synonym expansion turned out to be a cheap local C hash table lookup (src/core/wordnet.c), that cost justification mostly evaporated. Stage 7's query formulation step already re-filters synonym candidates via its own LLM call, providing a downstream safety net against noise from any non-content words that survive stopword removal | Stand up the Python sidecar (spaCy) for POS tagging only if the benchmarking stage (spec section 8, MS MARCO comparison) shows measurably worse precision/recall without it -- not before, per the spec's own stated principle: "engineer for the problem you have, not the problem you might have" |
| src/core/query_formulation.c | Output is a flat, unweighted term list, not the spec's fuller vision of "a boolean BM25 query with phrase groupings and term weights" (5.2.4). Matches what bm25_search() can actually consume today -- no boolean operators, phrase grouping, or per-term weighting exist anywhere in bm25.c | Add per-term weighting to bm25_search()/bm25_term_score() first (a real change to already-tested retrieval code), then extend query formulation's prompt/parsing to produce weighted output, if flat-term-list precision proves insufficient in practice |
| src/core/query_formulation.c | query_formulation_build_prompt() caps each candidate category (synonyms/hypernyms/hyponyms) at 8 words per term (QUERY_FORMULATION_MAX_CANDIDATES) -- an arbitrary first-N cut, not a ranked top-N, since TokenList carries no relevance ordering, just synset-iteration order. A highly polysemous word (e.g. "dog": 29 synonyms, 41 hyponyms) has most of its candidates silently excluded from the prompt | Track some relevance/frequency signal during WordNet resolution (e.g. WordNet's own sense-ordering, which the current design discards) so the cap keeps the most useful candidates rather than whichever happened to be encountered first |
| src/core/main.c | `lexis ingest <corpus_dir>` never clears the existing index first -- it only appends. Running it twice on the same corpus duplicates every passage rather than replacing them (terms/postings stay correct via get_or_create_term's dedup, but passage rows and therefore BM25's corpus stats double) | Add a `--rebuild` flag (or make it the default) that deletes the existing index file before ingesting, or detect and skip documents already present by name |
| src/core/main.c | Model ("openai/gpt-4o-mini"), chunk size/overlap (200/40), top-K (5), and all data paths are still hardcoded constants in main.c -- config/lexis.conf now exists and is parsed (config.c), but only for the testing/production `mode` setting, not these | Extend config.c's parser to cover these too, if hardcoded defaults ever prove insufficient for real use |

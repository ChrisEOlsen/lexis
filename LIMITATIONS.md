# Known Limitations

Deliberate MVP-scope tradeoffs, not bugs. Track file, limitation, future upgrade.

| File | Limitation | Future Upgrade |
|---|---|---|
| src/core/tokenizer.c | ASCII-only normalization. Any byte >= 0x80 treated as delimiter — non-ASCII text gets split/dropped (e.g. "café" → "caf", "é" lost) | Add UTF-8-aware case folding/normalization (e.g. utf8proc) or ICU if non-English corpora become a requirement (spec section 9) |
| src/core/tokenizer.c | Internal apostrophes no longer fragment ("don't" stays one token), but there's still no contraction/expansion normalization — "don't" and "do not" share zero tokens, and possessives aren't stripped ("Okafor's" stays "okafor's", won't match a bare "Okafor" elsewhere in the text). Deliberately not attempting to tell contraction from possessive by spelling alone — a strip-trailing-'s rule would silently turn "isn't" into "isn", inverting a negation | Contraction-expansion table or NLP-based normalization in Python sidecar (pairs with POS tagging, spec 5.2.2) — not the C tokenizer's job |
| src/core/tokenizer.c | Word buffer capped at 256 bytes (WORD_BUFFER_SIZE). Words/runs longer than that are silently truncated, not rejected or logged | Revisit only if real corpus data shows pathological long non-space runs; consider explicit rejection + logging instead of silent truncation |
| src/core/pg_store.c | pg_store_get_or_create_term()/pg_store_get_or_create_terms() use INSERT ... ON CONFLICT (term) DO NOTHING plus a re-SELECT, not DO UPDATE ... RETURNING id -- DO UPDATE takes a row lock even for a no-op self-assignment, and under real concurrent writers that caused genuine Postgres deadlocks (verified: "deadlock detected ... while inserting index tuple ... in relation terms"). DO NOTHING still doesn't eliminate deadlocks entirely -- Postgres's ON CONFLICT uses "speculative insertion" internally, and concurrent speculative inserts on the same unique index can still deadlock (also verified directly, same error, with DO NOTHING). This is exactly the contention bulk_ingest.c's three-phase design (see SPEED.md) was built to avoid structurally -- its Phase 2 worker pool never calls these functions at all, only Phase 3's single-writer finalize pass touches `terms` | These two functions currently have no production caller (bulk_ingest.c's Phase 2/3 use a different, staging-table-based path instead) -- kept as tested, documented PgStore API surface for any future caller needing single-term resolution outside the bulk pipeline |
| src/core/pg_store.c | postings stores one uncompressed SQL row per (term, passage) pair -- measured ~29.3 bytes/row (data + its B-tree index combined) on the SQLite version via dbstat; Postgres's row/index overhead is a different number but the same class of gap versus a real compressed inverted index (delta-encoded passage IDs + varint, e.g. Lucene/PISA-style, ~1-3 bytes/posting). Projected against MS MARCO's 8.8M passages (spec 8.2), a naive extrapolation put the SQLite schema's full index around ~14-15GB versus the ~1.5-2GB commonly cited for a compressed BM25 index over the same dataset -- not directly comparable formats, but a real footprint difference worth knowing about before a large ingest; not yet re-measured against Postgres's actual on-disk size | Replace one-row-per-posting with a compressed postings list per term (a delta-encoded/varint BLOB of passage_id+term_frequency pairs, decoded on read in bm25.c), matching real inverted-index compression at the cost of "postings queryable via plain SELECT" |
| src/core/ingest.c | ingest_read_file() loads an entire document into memory with no size guard. Assumes each document (a research paper, legal document, single codebase file, etc. per spec's own examples) is individually small — the corpus is many separate reasonably-sized files, not one unbounded blob | Add a max-file-size check (reject + log, don't silently attempt a huge malloc) if a real corpus ever presents a pathologically large single document; until then this is unexercised complexity |
| src/core/wordnet.c | wordnet_parse_data_line() assumes a hypernym/hyponym pointer's target synset shares the source synset's part of speech. Holds in practice for these two relations, but the file format technically allows cross-POS pointers | Store the pointer's own `pos` field (currently read and discarded) if a real lookup ever needs to follow a cross-POS hypernym/hyponym chain |
| src/core/wordnet.c | wordnet_load_data_file() treats any single unparseable line as a hard failure for the whole file, rather than skipping the bad line and continuing. Deliberate: this is trusted, official WordNet data, so a parse failure indicates a real bug in the parser, not malformed input worth silently tolerating | Revisit only if this is ever pointed at a modified/non-official WordNet distribution where a skip-and-continue policy might be more appropriate |
| (no current file -- Stage 6) | POS tagging is deferred entirely -- the query pipeline sends stopword-filtered terms straight to WordNet lookup with no noun/verb/adjective gate in front of it. Originally planned as a Python sidecar (spaCy) because the spec assumed synonym expansion itself would be the expensive step (Python/NLTK), making it worth pre-filtering first; once synonym expansion turned out to be a cheap local C hash table lookup (src/core/wordnet.c), that cost justification mostly evaporated, and the never-implemented sidecar scaffold (src/sidecar/, all empty stub files) was removed entirely rather than left as dead placeholder code. Stage 7's query formulation step already re-filters synonym candidates via its own LLM call, providing a downstream safety net against noise from any non-content words that survive stopword removal | Build a Python sidecar (spaCy) for POS tagging only if the benchmarking stage (spec section 8, MS MARCO comparison) shows measurably worse precision/recall without it -- not before, per the spec's own stated principle: "engineer for the problem you have, not the problem you might have" |
| src/core/query_formulation.c, src/core/bm25.c | Partially closed 2026-08-14: bm25_search_weighted() adds per-term score weights (originals 1.0, expansions LEXIS_EXPANSION_WEIGHT 0.4) plus a distinct-term coordination bonus. Still short of the spec's fuller vision (5.2.4): no boolean operators or phrase groupings, and the weights are a two-tier original/expansion policy, not per-term relevance | Extend to phrase groupings/boolean structure only if flat weighted terms prove insufficient in practice |
| src/core/query_formulation.c | query_formulation_build_prompt() caps each candidate category (synonyms/hypernyms -- hyponyms are no longer offered at all, see the expansion redesign in the local_llm_client.c row) at 8 words per term (QUERY_FORMULATION_MAX_CANDIDATES) -- an arbitrary first-N cut, not a ranked top-N, since TokenList carries no relevance ordering, just synset-iteration order. A highly polysemous word (e.g. "dog": 29 synonyms) has most of its candidates silently excluded from the prompt | Track some relevance/frequency signal during WordNet resolution (e.g. WordNet's own sense-ordering, which the current design discards) so the cap keeps the most useful candidates rather than whichever happened to be encountered first |
| src/core/main.c | `lexis bulk-ingest <tsv_path>` never clears the existing index first -- it only appends. Running it twice on the same corpus duplicates every passage rather than replacing them (terms stay correct via Phase 3's ON CONFLICT DO NOTHING dedup, but passage rows and therefore BM25's corpus stats double) | Add a `--rebuild` flag (or make it the default) that truncates passages/terms/postings before ingesting, or detect and skip documents already present by name |
| src/core/main.c | Chunk size/overlap (200/40) and all data paths are still hardcoded constants in main.c, and the retrieval depth/trim policy is likewise compile-time (LEXIS_SEARCH_* in bm25.h, shared with the app since the 2026-08-14 pipeline unification) -- config/lexis.conf is parsed (config.c) for the testing/production `mode` setting and, since the E4B upgrade, `model_path` (previously hardcoded separately in the CLI, app, eval harness, and depth_ab, which drifted every model swap) | Extend config.c's parser to cover the rest too, if hardcoded defaults ever prove insufficient for real use |
| src/core/local_llm_client.c | Full OpenRouter-to-local migration (openrouter_client.c/.h deleted): every LLM call site runs a local GGUF model via llama.cpp's embedded C API. There are now five (query reformulation, tool routing, summary construction, grounded answering, conversational answering), not the two this entry originally described, and the model has changed three times since -- Llama-3.2-3B-Instruct-Q4_K_M, then Qwen3.5-2B, then gemma-4-E2B-it-Q4_K_M (3.1GB, chosen against the old 8GB machine), now gemma-4-E4B-it-Q4_K_M (5.0GB, adopted on the 24GB M5 machine; the path now comes from config/lexis.conf's `model_path`). A "regression" observed at the swap (E4B dropping `tut`/`king` from term selection) turned out to be a latent lemmatizer bug, not model behavior: lemmatizer.c was missing morphy's return-unchanged-if-already-in-WordNet guard, so base forms that merely look inflected were mangled ("king" -> "k", "ring" -> "re", "sing" -> "se") at BOTH index and query time -- E2B had been masking it by sloppily copying question words the prompt never listed, E4B's stricter instruction-following exposed it. Fixed (see lemmatizer.c step 2 and test_lemmatizer.c's king/kings/saw tests); any index built before the fix must be re-ingested. The fix costs ingest throughput (one extra wordnet_lookup per token): 9,062 passages/sec vs 13,595 on the same 200K slice/machine. Still open, cleanly exposed now that formulation input is sane: selected expansion terms are not deduplicated ("monarch" can appear twice, double-counting its BM25 contribution) and generic expansions (monarch/sovereign) can outscore rare high-signal question terms (tut) -- the "king tut" query now formulates correctly yet still misses its gold passage in the top-5. Measured on the 70 dev queries whose gold passage is inside the 200K slice (post-lemmatizer-fix index, gemma-4-E4B): plain lemmatized terms MRR@10 0.219 / R@10 0.536 / R@100 0.769, with the original LLM+WordNet expansion 0.142 / 0.414 / 0.690 -- net-negative on every metric. REWORKED 2026-08-14 (sense-filter prompt with originals enforced in code, hyponyms dropped, expansions deduped/validated/lowercased, LEXIS_EXPANSION_WEIGHT 0.4 in bm25_search_weighted(), coordination bonus): expansion now measures 0.222 / 0.550 / 0.776 -- ahead of the plain baseline on every metric. Same-day DelucionQA starter run through the real app pipeline: 30/30 routed SEARCH, 0 refusals, mean 29.3s. After unifying CLI/app onto one retrieval pipeline (expansion in both, shared LEXIS_SEARCH_* depth/trim): starter run repeats 30/30 SEARCH / 0 refusals, coverage statistically unchanged (mean 53.9% vs 53.7%), +2.7s mean latency (32.0s) for the expansion call -- on DelucionQA's union-of-gold corpus retrieval had little headroom, so flat-at-a-latency-cost is the expected result there; the expansion's measured value is on MS MARCO and as the only non-embeddings answer to zero-postings intent terms. Gains over plain are modest; the zero-postings intent-term mechanism (a query word with no index match, e.g. "functions") remains addressable only by expansion or embeddings. The index is unaffected by those swaps: it stores terms and postings, nothing model-derived. The migration was chosen after rejecting the OpenRouter API's per-query cost for a ~9,260-query MRR@10/Recall@K eval, and Ollama's separate-HTTP-server model in favor of true in-process linking (matching the project's native-app direction). Verified real: linked a standalone test program against `llama.h`/`libllama.dylib` (Homebrew, /opt/homebrew/Cellar/llama.cpp), ran a real generation, and confirmed Metal GPU offload auto-detects with a ~5.7GB recommendedMaxWorkingSetSize on this 8GB M2 -- the real number the model size was chosen against, since Postgres and the OS both need headroom on the same machine. (Originally measured while Postgres still ran under Docker Desktop, which needed more headroom than the native install this project later moved to entirely -- see CURRENT_STATE.md) | Not yet measured under concurrent load -- revisit if Metal + Postgres memory pressure ever becomes a real problem in practice |
| src/core/local_llm_client.c | main.c's run_query() loads the model fresh (llama_model_load_from_file + Metal shader compilation) on every single CLI invocation -- measured ~9-19s of that one-time cost per process, dominating a single query's wall time. Fine for one-off CLI queries; would be a real problem for the paused MS MARCO eval plan (~9,260 queries), which needs the model loaded once and reused across the whole run, not re-loaded per query | Addressed for every batch path: `lexis eval` (src/core/eval.c) runs the MS MARCO retrieval eval as one long-lived process (one model load per run), and app/src/eval_main.cpp (`lexis_eval`) does the same for the chat pipeline. Only one-off `lexis query` invocations still pay the load per process -- inherent to a one-shot CLI, not worth a resident daemon |
| src/core/local_llm_client.c | Sampling is greedy-only (llama_sampler_init_greedy(), no temperature/top-p/repetition penalty) -- deterministic and cheap, matching "fast, not creative," but with no repetition penalty a long grounded-generation prompt could in principle degenerate into token loops; not observed in manual testing so far, not yet stress-tested against long/adversarial contexts. n_ctx is 16384 and n_batch is set equal to it, which allocates a large Metal compute buffer -- relevant on an 8GB machine, where two processes each holding the model have been observed to hit Metal OOM. A prompt that doesn't fit is rejected cleanly (logged, returns NULL) rather than truncated or chunked | Add a repetition penalty sampler (llama_sampler_init_penalties()) if looping is ever observed in practice; consider decoupling n_batch from n_ctx if memory pressure on 8GB machines becomes routine |
| src/core/query_formulation.c, src/core/generation.c | Conversation history threaded into both chat LLM calls (query reformulation, generation) is windowed with a hard token-budget cutoff, not summarized -- each file's own window_history() walks the turns oldest-first and drops whatever doesn't fit its call's own budget under LOCAL_LLM_N_CTX (16384). A reference from far enough back in a long conversation is silently forgotten rather than fuzzily retained | Summarize turns before they fall out of the window into a running compact note carried alongside the live window, if a hard cutoff proves too lossy in practice -- not built now since it requires its own LLM call (more latency, more summarization-quality risk on a model this small) and there's no evidence yet that plain truncation is insufficient |
| src/core/corpus_summary.c | A group summary is built from a token-budgeted SAMPLE of each document -- the head plus evenly spaced excerpts (CORPUS_SUMMARY_EXCERPTS_PER_DOC=3), splitting the budget evenly across documents -- not from their full text. Deliberate: one LLM call per group instead of one per chunk, which is what makes the SUMMARY tool the fast path it exists to be. The cost is that a topic appearing only in a section that wasn't sampled can be absent from the summary, and therefore from any answer built on it. Excerpt boundaries are also cut on byte offsets using a conservative 3-bytes-per-token estimate, so a cut can land mid-word or mid-UTF-8-sequence -- harmless here, since the text is only ever fed to a tokenizer for gist extraction and never shown to the user | Map-reduce summarization (summarize every chunk, then summarize the summaries) for complete coverage, if sampled summaries prove to miss topics users actually ask about. Costs N+1 LLM calls per document -- minutes for a large PDF on a local model -- so it needs a reason beyond thoroughness |
| src/core/corpus_summary.c, src/core/pg_store.c | Cached summary staleness is keyed on document_count alone (public.corpus_summaries.document_count vs the group's current count). Coarse on purpose, and it cannot detect a document being replaced by a different one at the same count, nor a document's contents changing in place -- either leaves a summary describing a collection that no longer exists, with no signal that it is wrong | Key staleness on something content-derived (a hash over document names plus lengths, or a corpus-level updated_at bumped by ingest) if in-place replacement becomes a real workflow rather than a theoretical one |
| src/core/tool_router.c | Tool choice is a single one-shot LLM classification with no fallback path: once SUMMARY is chosen, a broad question is answered from the cached overview even if the detail it needs was never in that overview, and there is no escalation to reading the documents. The retired TOOL_READ_DOCUMENTS path (generation_generate_answer_from_documents(), still present in generation.c but no longer called) was what would have served that case | Add a second routing pass that can escalate SUMMARY -> full read when the summary-based answer is judged insufficient; deliberately deferred, since it doubles the routing latency on every broad question to rescue a case not yet observed in practice |
| src/core/generation.c | Enumeration answers ("list every X") are unstable on the local model, and not in a way any retrieval change reliably fixes. (Measured on gemma-4-E2B against a pre-lemmatizer-fix index -- re-measure on the current E4B/unified pipeline before trusting the specific numbers below.) Measured against a corpus whose manual lists exactly six license classes: with the same five retrieved passages -- all six classes verifiably present in the model's context -- the answer named 6/6 with one instruction wording and 5/6 (silently dropping Non-CDL Class C) with another, differing only in a semantically irrelevant sentence. Retrieval depth 10 produced 6/6; depth 20 fused a same-named label from an unrelated section ("Class C is for mopeds", from the moped Class A/B/C chart) into the answer; depth 30 collapsed the answer to one sentence and 4/6. Reordering the prompt so passages sit nearest the answer, and stripping the model's own prior turns out of the history, both made it slightly WORSE (5/6), which rules out the obvious "conversation history outweighs retrieved text" explanation. The failure mode is silent and confident: the model states "six types" and then lists five | Build a repeatable enumeration eval (several "list every X" questions x configurations, counted) before changing anything further -- single greedy-decode runs are single samples of a brittle system and have already produced two wrong root-cause diagnoses. If instability persists, stop asking the model to enumerate: extract list structure deterministically, or move enumeration to a larger model |
| src/core/query_formulation.c, app/src/QueryWorker.cpp | query_formulation_terms_union() stops the contextual rewrite from LOSING a discriminative term, but does not restore the raw question's retrieval quality: the union's raw and rewrite terms all ride at the same 1.0 "original" weight (bm25_search_weighted()'s tiers distinguish originals from WordNet expansions, not raw from rewrite -- the distinct-term coordination bonus only partially compensates). Measured pre-weighting: raw "What are the license classes?" (terms `license class`) put the two passages holding all six classes at ranks 1-2; the rewrite's terms (`different type drive license new york state`) found none of them; the union recovered only part of the way. Related, introduced by the 2026-08-14 pipeline unification: the sense-filter expansion prompt receives the REFORMULATED question, so if reformulation ever goes badly wrong, expansion now compounds it (candidates get sense-checked against a wrong rewrite), though the union still anchors the original question's terms in the search | Weight raw-question terms above rewrite-only terms via the existing per-term weights, or run raw and rewritten searches separately and merge the ranked lists; for the compounding risk, consider sense-filtering against the raw question when the rewrite diverges wildly from it |
| src/core/generation.c, src/core/local_llm_client.c | The model's reasoning pass is enabled for both user-facing answer generators (from retrieved passages, and from a group summary), and it roughly TRIPLES answer latency: measured 28.2s with thinking versus 9.9s without, on the same question, same 12 retrieved passages, same corpus. That cost is paid on every answer, including the majority that were already correct without it -- thinking was originally disabled precisely for this reason, on the theory that a grounded answer needs no deliberation. It was re-enabled because that theory failed on a real case: where every retrieved passage was legitimately on topic (a question about steering wheel buttons, against a manual that discusses the heated steering wheel in ~19 passages and the cruise-control buttons in one), the model with no opportunity to weigh them answered from the wrong one, and with thinking answered correctly. Enabling it also required LOCAL_LLM_MAX_NEW_TOKENS to go from 512 to 2048, since reasoning alone exceeded the old cap and the model never reached an answer. IMPORTANT: the 3x figure was ONE question, ONE run. MEASURED 2026-08-14 on the 30-question starter set (post-coordination-bonus retrieval, gemma-4-E4B, config `thinking=off` vs on): coverage statistically identical (mean 53.6% vs 53.9%), same failure questions in both arms, and on the crowded-topic question that originally motivated thinking, the no-thinking answer led with the RIGHT controls while the thinking answer led with the heater -- the coordination bonus now does at the retrieval layer what thinking was doing at generation. Latency 8.3s vs 32.0s mean (3.9x). `thinking` is now a config/lexis.conf setting (default on if unset; the checked-in conf ships off on this data). Caveat: 30 questions, single greedy run each -- the 913-question run (TESTING.md) is the fuller distribution | Re-verify at the 913-question scale; if a thinking-rescued shape reappears, implement conditional thinking (only when top BM25 scores are flat) rather than always-on |
| src/core/tool_router.c, src/core/local_llm_client.c | A failed model call is indistinguishable from a real routing decision. tool_router_choose_tool() returns TOOL_SEARCH_PASSAGES on allocation failure, a NULL reply, or an unparseable one -- deliberately, so an ambiguous decision still lands on the proven pipeline -- but the caller cannot tell that apart from the model actually answering SEARCH. Observed for real during testing on this 8GB machine: with the Qt app already holding the model, a second process hit Metal OOM (kIOGPUCommandBufferCallbackErrorOutOfMemory), every local_llm_chat_completion_multi() call returned NULL, and a 17-case routing check came back 10/17 'wrong' -- including "Hello how are you?" routing to SEARCH. Nothing in the return value said the model was unavailable. In the app the same condition would silently route every message to lexical search and then fail generation with "Could not answer that question", with no indication in the UI that the model call died rather than the answer being poor | Give the router an explicit failure return (or an out-parameter) separating "model unavailable" from "model chose SEARCH", so the UI can say the model is unavailable instead of showing a confidently wrong route. Same for the generation path. Related: n_batch is set equal to n_ctx (16384), which allocates a large Metal compute buffer -- worth revisiting if memory pressure on 8GB machines becomes routine rather than an artifact of running two model processes at once |
